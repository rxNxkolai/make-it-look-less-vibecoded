Kestrel

Kestrel is a scheduler for async work. It gives every call a lane with its own concurrency cap, rate limit, retry policy and priority, so the shape of your traffic is described in one place instead of scattered through the code that makes the requests.

v2.4.1 MIT 3.1 kB min+gzip 0 dependencies ESM + CJS TypeScript first

Every non-trivial front end eventually grows a hand-rolled scheduler: a counter that caps parallel fetches, a setTimeout that spaces out calls to a rate-limited endpoint, a retry loop bolted onto one particularly flaky request. Each piece is small. Together they are impossible to reason about, because no single place knows how much work is in flight.

Kestrel is that missing place. You declare the limits once, hand it functions, and it decides what runs when.

import { createQueue } from 'kestrel'

const queue = createQueue({ concurrency: 4, rate: '10/s' })

// Fires immediately if a slot is free, otherwise waits its turn.
const results = await Promise.all(
  ids.map(id => queue.run(() => fetch(`/api/items/${id}`).then(r => r.json())))
)
import { createQueue } from 'kestrel'

export const queue = createQueue({
  concurrency: 8,
  lanes: {
    search:   { concurrency: 2, rate: '10/s' },
    upload:   { concurrency: 1, retries: 3, timeout: 30_000 },
    prefetch: { concurrency: 4, priority: -1 }
  }
})

queue.lane('search').run(() => searchItems(term))
queue.lane('prefetch').run(() => warmCache(nextPage))
import { queue } from './queue.js'

// wrap() returns a function with the same signature, already scheduled.
export const searchItems = queue.lane('search').wrap(async (term, { signal } = {}) => {
  const res = await fetch(`/api/search?q=${encodeURIComponent(term)}`, { signal })
  if (!res.ok) throw new Error(`search failed: ${res.status}`)
  return res.json()
})

// Callers never think about the queue.
const hits = await searchItems('peregrine')
Scope

Kestrel schedules work inside one process. It is not a job queue and it does not coordinate across servers, tabs or workers. If you need durable jobs or a shared limit across instances, see when not to use Kestrel.

Installation

Kestrel ships as ESM and CJS with bundled type definitions. There is no peer dependency and no postinstall step.

npm install kestrel
pnpm add kestrel
yarn add kestrel
bun add kestrel
deno add npm:kestrel
# or import it directly, no install required
# import { createQueue } from 'npm:kestrel@2.4.1'
<script type="module">
  import { createQueue } from 'https://esm.sh/kestrel@2.4.1'
  const queue = createQueue({ concurrency: 3 })
</script>

TypeScript users need nothing extra. Queue, Lane, TaskOptions and the error classes are all exported, and queue.run() infers its return type from the task you hand it.

Quick start

A queue, four slots, and a rate limit that matches what the upstream API actually allows.

import { createQueue, isCancelled } from 'kestrel'

const queue = createQueue({
  concurrency: 4,        // never more than 4 requests in flight
  rate: '20/s',          // and never more than 20 started per second
  retries: 2,            // retry twice on failure, exponential backoff
  timeout: 8_000         // abort any task that runs longer than 8s
})

async function loadThumbnail(id, signal) {
  const res = await fetch(`/api/thumbnails/${id}`, { signal })
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.blob()
}

const controller = new AbortController()

try {
  const blobs = await Promise.all(
    ids.map(id => queue.run(sig => loadThumbnail(id, sig), {
      signal: controller.signal,
      priority: isVisible(id) ? 10 : 0
    }))
  )
  render(blobs)
} catch (err) {
  if (!isCancelled(err)) throw err
}

Three things are worth noticing in that snippet.

  • The task receives its own AbortSignal. Kestrel aborts it on timeout, on cancellation, and when the queue is cleared, so you forward it to fetch and stop thinking about teardown.
  • priority is evaluated when the task is enqueued, not when it starts. Visible thumbnails jump the line ahead of everything already waiting.
  • Failures reject the promise returned by run() after the retry budget is spent. Kestrel never swallows an error.
Tip

Create the queue once at module scope and import it. A queue created inside a component or request handler is a queue with a concurrency limit of one caller, which is another way of saying no limit at all.

Why Kestrel

The same program, written twice.

Concurrency control on its own is easy. A dozen lines get you a semaphore. The cost shows up later, when the semaphore needs to also understand rate limits, retries, timeouts, cancellation and ordering, and every one of those features has to be threaded through the same fragile counter.

Hand-rolled

let active = 0
const waiting = []
let lastCall = 0

async function limited(fn, attempt = 0) {
  if (active >= 4) await new Promise(resolve => waiting.push(resolve))
  const gap = Date.now() - lastCall
  if (gap < 100) await sleep(100 - gap)   // crude 10/s
  active++
  lastCall = Date.now()
  try {
    return await fn()
  } catch (err) {
    if (attempt < 2) return limited(fn, attempt + 1)   // recursion re-queues, so
    throw err                                          // the retry waits behind
  } finally {                                          // everything else. Oops.
    active--
    waiting.shift()?.()
  }
}

That code has at least three bugs, and every one of them only shows up under load: the rate limiter drifts because it measures the gap before acquiring a slot, retries lose their place in the queue, and there is no way to cancel anything. Adding priority means rewriting waiting as a heap.

With Kestrel

import { createQueue } from 'kestrel'

const queue = createQueue({ concurrency: 4, rate: '10/s', retries: 2 })

const limited = queue.wrap(fn)

Retries keep their slot instead of going to the back of the line. The rate limiter is a sliding window measured at dispatch. Cancellation is an AbortSignal away, and priority is a number.

Core concepts

Four nouns. Everything in the API is one of them.

QueuecreateQueue()
The root scheduler. Owns the global concurrency cap and the default policy that every lane inherits. One queue per external system is the usual shape: one for your API, one for the image CDN, one for analytics.
Lanequeue.lane(name)
A named slice of a queue with its own limits. Lanes compete for the queue's global slots but can never exceed their own cap, which is how a burst of prefetches is prevented from starving user-initiated searches. Lanes are created on first use and are cheap.
Policyretries, rate, timeout
The rules applied to a task: how many attempts, how long to wait between them, how fast tasks may start, and when to give up. Policy is resolved per task by merging queue defaults, lane options and per-call options, in that order.
Taskqueue.run(fn, options)
One unit of work: a function, a priority, and a signal. Kestrel calls it with a fresh AbortSignal and returns a promise that settles exactly once, after retries are exhausted or on the first success.

Walkthrough: a polite crawler

Four steps, building up a job that reads 40,000 records from an API that allows 600 requests per minute and 5 concurrent connections.

  1. Bound the concurrency

    Start with the number the upstream documentation gives you. Kestrel has no default concurrency, on purpose: the right value is a property of the service you are calling, not of the library.

    import { createQueue } from 'kestrel'

const api = createQueue({ concurrency: 5 })

for (const id of recordIds) {
  api.run(() => fetchRecord(id))     // returns a promise, does not await
}

await api.drain()                    // resolves when everything has settled

    Note that run() is fire-and-track. You can await each promise individually, collect them with Promise.all, or ignore them and await drain() for the whole batch.

  2. Add the rate limit

    Concurrency alone will not keep you under a per-minute budget. Five fast requests finish in 50 ms and immediately start five more. The rate option adds a sliding window measured at the moment a task is dispatched.

    const api = createQueue({
  concurrency: 5,
  rate: '600/m'        // also accepts '10/s', '1/250ms', or { max: 600, window: 60_000 }
})
    How the window works

    Kestrel records a timestamp per dispatch and keeps the last max of them. A new task starts only when the oldest timestamp has fallen out of the window. This is a true sliding window, not a token bucket that refills in bursts, so you will never send 600 requests in the last second of one minute and 600 more in the first second of the next.

  3. Split the traffic into lanes

    A crawl is not one kind of request. Listing pages are cheap and drive everything else; detail fetches are the bulk of the work; writes must never run in parallel. Lanes let one queue express all three without three separate limiters fighting over the same budget.

    const api = createQueue({
  concurrency: 5,
  rate: '600/m',
  lanes: {
    index:  { concurrency: 1, priority: 10 },              // drives the crawl, always first
    detail: { concurrency: 4, retries: 3 },                // the bulk of the work
    write:  { concurrency: 1, retries: 5, timeout: 20_000 }
  }
})

const index  = api.lane('index')
const detail = api.lane('detail')
const write  = api.lane('write')

for await (const page of paginate(url => index.run(() => fetchJson(url)))) {
  for (const ref of page.items) {
    detail.run(() => fetchJson(ref.href))
      .then(record => write.run(() => save(record)))
  }
}

    Because index carries a priority of 10, a listing request will always take the next free slot ahead of the thousands of queued detail fetches. The crawl keeps moving instead of stalling behind its own backlog.

  4. Wire up cancellation and shutdown

    Long-running jobs need a stop button. Pass a signal per task, or clear the queue wholesale. Either way, in-flight tasks receive an abort on the signal Kestrel handed them.

    const stop = new AbortController()
process.on('SIGINT', () => stop.abort())

const detail = api.lane('detail')

detail.run(signal => fetchJson(ref.href, { signal }), { signal: stop.signal })

// On shutdown: stop accepting work, let in-flight tasks finish, then exit.
stop.signal.addEventListener('abort', async () => {
  api.pause()                       // queued tasks stay queued, nothing new starts
  await api.drain({ inFlightOnly: true })
  api.clear({ reason: 'shutdown' }) // pending tasks reject with TaskCancelled
  process.exit(0)
})
    Tip

    isCancelled(err) is the safe way to tell a deliberate cancellation apart from a real failure. It returns true for both TaskCancelled and a native AbortError, so it works whether the abort was caught by Kestrel or by fetch.

API reference

The complete surface. Nine functions and three error classes.

createQueue(options)

Creates a queue. concurrency is required; everything else is optional and becomes the default policy for every lane and task in the queue.

const api = createQueue({
  concurrency: 6,
  retry: {
    attempts: 5,
    backoff: 'exponential',
    delay: 250,
    jitter: 'full',
    on: (err, attempt) => {
      if (err.status === 429) return true          // always retry throttling
      if (err.status >= 500) return attempt < 3    // give up on 5xx sooner
      return false                                 // never retry 4xx
    }
  }
})

Lane

A lane exposes the same task-running surface as a queue, scoped to itself. lane.size and lane.pending report that lane only; lane.queue gives you the parent back.

interface Lane {
  readonly name: string
  readonly queue: Queue
  readonly size: number
  readonly pending: number
  readonly saturated: boolean

  run<T>(task: (signal: AbortSignal) => Promise<T>, options?: TaskOptions): Promise<T>
  wrap<A extends unknown[], T>(fn: (...args: A) => Promise<T>, options?: TaskOptions): (...args: A) => Promise<T>
  drain(options?: DrainOptions): Promise<void>
  clear(options?: ClearOptions): number
  configure(options: Partial<LaneOptions>): void
}

Events

Events exist for instrumentation. They are synchronous and must not throw; a handler that throws is reported through queue.on('error') and otherwise ignored.

Framework adapters

Thin bindings that connect a queue to a component lifecycle. Each is published separately and each is under 1 kB.

import { useTask } from 'kestrel/react'
import { queue } from './queue.js'

export function SearchResults({ term }) {
  // Re-runs on term change, cancels the previous task, cancels on unmount.
  const { data, error, status } = useTask(
    queue.lane('search'),
    signal => fetch(`/api/search?q=${term}`, { signal }).then(r => r.json()),
    [term]
  )

  if (status === 'pending') return <Spinner />
  if (error) return <ErrorState error={error} />
  return <List items={data.items} />
}
import { useTask } from 'kestrel/vue'
import { queue } from './queue.js'

export function useSearch(term) {
  // term is a ref; the task re-runs and cancels automatically.
  return useTask(
    queue.lane('search'),
    signal => fetch(`/api/search?q=${term.value}`, { signal }).then(r => r.json()),
    [term]
  )
}
import { task } from 'kestrel/svelte'
import { queue } from './queue.js'

// A readable store: { status, data, error }
export const results = task(
  queue.lane('search'),
  (signal, term) => fetch(`/api/search?q=${term}`, { signal }).then(r => r.json())
)

// results.run('peregrine') cancels any in-flight run first.
import { pipeline } from 'node:stream/promises'
import { scheduled } from 'kestrel/node'
import { queue } from './queue.js'

// A Transform that applies backpressure from the queue to the stream.
await pipeline(
  createReadStream('urls.txt'),
  splitLines(),
  scheduled(queue.lane('detail'), async (url, signal) => {
    const res = await fetch(url, { signal })
    return res.json()
  }),
  writeRecords()
)
Note

The adapters do not create queues. You pass in a queue or lane you already own, which keeps the limits declared in one file rather than implied by whichever component happened to render first.

Recipes

Patterns that come up often enough to be worth writing down.

Cancel in-flight work on navigation

Route changes make most pending requests worthless. Give each route an AbortController and abort it on exit; the queue drops both running and queued work for that route.

let routeAbort = new AbortController()

router.beforeEach(() => {
  routeAbort.abort()
  routeAbort = new AbortController()
})

export const routeSignal = () => routeAbort.signal

// in a loader
const data = await queue.run(s => fetchJson(url, { signal: s }), { signal: routeSignal() })

Deduplicate identical in-flight requests

Kestrel does not cache, but key makes it collapse concurrent duplicates: a second task with a key that is already running attaches to the first result instead of starting a new task.

const user = id => queue.run(
  signal => fetchJson(`/api/users/${id}`, { signal }),
  { key: `user:${id}` }
)

// One network request, three consumers.
const [a, b, c] = await Promise.all([user(7), user(7), user(7)])
Careful

Deduplication is scoped to tasks that are queued or running right now. Once a task settles the key is released, so this is request collapsing, not caching. Pair it with a real cache if you want results to survive.

Boost what the user can see

Priority is read at enqueue time, so recomputing it as the viewport changes needs a re-enqueue. For lists, the cheaper move is to cancel off-screen work and re-add it at a lower priority.

const observer = new IntersectionObserver(entries => {
  for (const entry of entries) {
    const id = entry.target.dataset.id
    controllers.get(id)?.abort()

    const ac = new AbortController()
    controllers.set(id, ac)
    queue.run(s => loadThumbnail(id, s), {
      signal: ac.signal,
      priority: entry.isIntersecting ? 10 : -5
    }).catch(ignoreCancelled)
  }
})

Graceful shutdown in Node

async function shutdown(signal) {
  logger.info(`${signal} received, draining`)
  server.close()
  api.pause()

  const timer = setTimeout(() => {
    logger.warn('drain timed out, aborting in-flight work')
    api.clear({ abortRunning: true, reason: 'shutdown-timeout' })
  }, 15_000)

  await api.drain()
  clearTimeout(timer)
  process.exit(0)
}

for (const sig of ['SIGINT', 'SIGTERM']) process.on(sig, () => shutdown(sig))

Testing with fake timers

Kestrel reads the clock through an injectable now and setTimeout, so backoff and rate windows work with any fake-timer implementation without await sleep() in your tests.

import { createQueue } from 'kestrel'
import { vi, test, expect } from 'vitest'

test('spaces dispatches to the configured rate', async () => {
  vi.useFakeTimers()
  const started = []
  const queue = createQueue({ concurrency: 10, rate: '2/s' })

  for (let i = 0; i < 6; i++) queue.run(async () => started.push(Date.now()))

  await vi.advanceTimersByTimeAsync(2_500)
  expect(started).toHaveLength(6)
  expect(started[5] - started[0]).toBeGreaterThanOrEqual(2_000)
})

When not to use Kestrel

  • You only need a concurrency cap. p-limit is under a kilobyte and does exactly that. Reach for Kestrel when the second requirement arrives.
  • You need a shared limit across processes or machines. Kestrel's state lives in one JavaScript heap. Use a Redis-backed limiter, or push the limit into a gateway.
  • You need durable jobs. Nothing survives a reload or a crash. If work must not be lost, you want a real job queue such as BullMQ or a hosted worker service.
  • Your bottleneck is the server. Client-side scheduling smooths the traffic you send; it does not fix an endpoint that takes four seconds. Measure first.

Frequently asked

Does cancelling a task abort the underlying fetch?

Only if you forward the signal. Kestrel calls your task with an AbortSignal and aborts it, but it cannot reach inside fetch on your behalf. Pass it through:

queue.run(signal => fetch(url, { signal }))   // aborts the request
queue.run(() => fetch(url))                   // request keeps going, result discarded

In the second form the promise still rejects immediately with TaskCancelled, and the slot is released, but the network request runs to completion in the background.

What happens to queued tasks when I call pause()?

They stay queued, in order, with their priorities intact. pause() stops dispatch only; running tasks are never interrupted. Call resume() and the queue picks up exactly where it left off. To actually discard queued work, use clear(), which rejects each pending task with TaskCancelled.

Do retries count against the rate limit?

Yes. The rate window counts dispatches, and a retry is a dispatch, because from the server's point of view it is another request. A retry does keep its concurrency slot rather than going to the back of the queue, so a retried task is not penalised twice.

If the error carries a Retry-After header and respectRetryAfter is on, that value overrides the computed backoff whenever it is longer.

Is scheduling fair across lanes?

Not strictly. Kestrel picks the highest-priority waiting task from any lane that is below its own cap, breaking ties FIFO. Lanes with equal priority therefore interleave naturally, but a lane that always enqueues at priority 10 will always win. That is deliberate: fairness is a policy, and the library would rather you state it than infer it.

If you need round-robin, give every lane the same priority and cap each one at roughly concurrency / laneCount.

Can I change limits at runtime?

Yes. lane.configure({ concurrency, rate, retries }) takes effect on the next dispatch decision. Lowering concurrency does not abort anything already running; the queue simply stops starting new tasks until it is back under the new cap. A common use is backing off when the server starts returning 429s:

queue.on('task:settle', ({ lane, ok, error }) => {
  if (!ok && error?.status === 429) {
    const l = queue.lane(lane)
    l.configure({ concurrency: Math.max(1, l.concurrency - 1) })
  }
})
Can the queue be persisted or resumed?

No. A task is a closure, and closures cannot be serialised. If you need work to survive a reload, persist the inputs yourself and rebuild the queue on start-up. That is usually a handful of lines and keeps the persistence format under your control rather than the library's.

How is 3.1 kB measured?

Minified with esbuild and gzipped, importing everything the package exports. A realistic app that imports only createQueue and isCancelled tree-shakes down to about 2.2 kB. The React adapter adds 0.6 kB. These numbers are asserted in CI, so a pull request that regresses them fails.

Why is there no default concurrency?

Because any default would be wrong. Infinity quietly disables the only feature you installed the library for, and a small number like 4 silently throttles a service that would happily take 50. Requiring the value forces a five-second conversation with the upstream documentation, which is exactly the conversation worth having.

Contributing

Kestrel is maintained in the open. Issues, discussions and pull requests all live on GitHub.

The test suite runs on fake timers and is fast; a full run is under three seconds. Scheduling bugs are usually reproducible as a deterministic test, and a failing test attached to an issue is the quickest path to a fix.

git clone https://github.com/kestreljs/kestrel
cd kestrel
pnpm install
pnpm test            # vitest, fake timers, ~3s
pnpm test:size       # asserts the bundle budget
pnpm bench           # dispatch throughput against p-queue and bottleneck

Two things to know before opening a pull request. Kestrel has a hard rule of zero runtime dependencies, so a change that adds one needs a strong argument. And the bundle budget is enforced: if a feature costs more than about 200 bytes, it probably belongs in an adapter package rather than the core.
